# Black Start Manager: durable format

This document describes the bytes the store owns. Everything is little-endian and
length-explicit; nothing is inferred from the surrounding file.

## Store directory

    <root>/store.manifest                 one authoritative generation
    <root>/store.lock                     exclusive writer lock (kernel-owned)
    <root>/snapshot-<16 digits>.bsm       one published state generation
    <root>/journal-<16 digits>.log        one append-only record segment
    <root>/<artifact>.tmp                 staged publication, never authoritative

The lock file's existence is not authority: authority is the successful exclusive open of
that file, which the operating system releases when the holder dies.

## Manifest

Canonical JSON with a strict schema:

    {
      "format_version": 1,
      "generation": <u64>,              snapshot generation, starts at 1
      "epoch": <u64>,                   store epoch, incremented on every open
      "last_incarnation": <32 hex>,     the process incarnation that last opened it
      "snapshot": {"name": ..., "digest": <64 hex>, "sequence": <u64>, "chain": <64 hex>},
      "journal":  {"name": ..., "base_sequence": <u64>},
      "manifest_digest": <64 hex>       SHA-256 over the canonical manifest without this field
    }

Decoding rejects unknown fields, a mismatched digest, an unsupported version, a name that
is not a store artifact (including anything containing a path separator), a journal base
sequence that differs from the snapshot sequence, and a zero generation or epoch.

## Snapshot file

    offset  size  field
    0       4     magic "BSMS"
    4       2     format version (1)
    6       2     reserved, must be zero
    8       8     sequence: the last journal sequence included
    16      8     payload length
    24      4     CRC-32C of the payload
    28      4     CRC-32C of bytes [0, 28)
    32      n     payload: canonical JSON
    32+n    32    SHA-256 over bytes [0, 32+n)

The payload is the manager's session table: format version, incarnation, and one entry per
session with its compiled plan and its committed record. Every nested value is canonical
JSON and is decoded strictly, so a snapshot that does not decode to a consistent session
table is refused.

## Journal frame

    offset  size  field
    0       4     magic "BSMJ"
    4       2     format version (1)
    6       2     reserved, must be zero
    8       8     sequence
    16      2     record kind
    18      2     reserved, must be zero
    20      4     payload length
    24      4     CRC-32C of the payload
    28      4     CRC-32C of bytes [0, 28)
    32      n     payload: canonical JSON object
    32+n    32    chain digest

The chain digest is SHA-256 over the previous chain digest, the frame header (32 bytes), and
the payload. The first frame of a segment chains from the snapshot's chain value, which the
manifest carries. A record is committed when the frame is written and flushed.

Record kinds: 1 session established, 2 session replanned, 3 authority re-established,
4 evidence admitted, 5 attempt recorded, 6 attempt settled, 7 attempt resolved, 8 stage
advanced, 9 session held, 10 session resumed, 11 session aborted, 12 session completed,
13 session superseded, 14 sessions demoted, 15 adjacent-owner ledger entry.

## Recovery rules

1. A missing manifest with an empty directory (or no directory) initializes a new store when
   the caller allowed it. A missing manifest with artifacts present is ambiguous and refused.
2. The manifest is decoded strictly and its digest verified.
3. The snapshot it names must exist, decode, and match its sequence and digest.
4. Journal frames are read in sequence order, verifying the header checksum, the payload
   checksum, the chain link, the payload schema, and the record kind.
5. An incomplete trailing frame, or a frame whose header checksum fails with no valid frame
   after it, is a torn tail: it is discarded and reported. A frame whose checksum fails with
   valid frames after it, a chain break, a payload checksum mismatch on a complete frame, or
   a well-formed header with an unsupported version is corruption and is refused.
6. Artifacts the manifest does not name are orphans from an interrupted publication: they
   are removed after recovery, and never trusted.

## Path safety

Artifact names are generated by the library and validated on the way back in: a single path
component, at most 128 characters from `[A-Za-z0-9._-]`, no leading dot, no separator, no
relative path name, and no Windows reserved device name. Store roots are validated for
length, control characters, invalid UTF-8, trailing spaces or dots, and reserved names, and
absolute paths longer than the classic Windows limit are expressed with the extended-length
prefix after normalizing separators.
